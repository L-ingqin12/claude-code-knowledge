# 预训练迷你 Kimi K3 — 实录章节总结

See also: [[Articles-Index]] | [[AI-Links-KB-Home]] | [[AI大模型开发]] | [[AGENTS]]

> [!abstract] 章节主旨
> 2026-07-27 Moonshot 发布 Kimi K3（2.8T 总参数、104B 激活、96 分片 1.561TB）。九天之后，作者用 **一块 H200、$252.35、5B tokens** 复刻了一个「迷你 K3」：**结构保留、规模不保留**。本章是全书第一章，先把「到底训练了什么」一次说清。

## 一、一次训练的一张表（全部来自运行遥测）

| 项 | 值 |
|---|---|
| 模型 | 1.02B 总参，145M 激活，61M 非嵌入 |
| 硬件 | 单卡 H200，$4.54/小时 |
| 每步 tokens | 131,072（4096 seq × 4 × 8 累积） |
| 步数 / tokens | 38,147 步 / 5,000,003,584 tokens |
| 峰值学习率 | 6.00e-4，warmup–stable–decay（step 32,430 起衰减） |
| Loss | step 0 = 12.100 → 结束 = 2.62 |
| 结束时死亡专家 | 0.0% |
| 成本 | **$252.35** |

- **Loss 起点是正确性检查**：词表 163,840 的均匀分布交叉熵 = ln(163,840) = **12.007**；step-0 loss 12.100 与之吻合，说明初始化与损失函数无误（微超额来自 embedding 与输出投影绑定时 logits 携带的少量结构）。此后的每个数字才是结果。
- 「迷你」的含义：约 1/2700（2.8T ÷ 1.02B）；从未指令微调，只做一件事——预测下一个 token；但拥有 K3 同款架构（同 3:1 注意力栈、同 aux-loss-free 的 MoE 路由、同激活函数、同 163,840 词表分词器）。

## 二、语料与去污染

- 5B tokens 抽取自 **104.80B tokens 六源语料**，分词前完成去污染。
- 方法：对 8 个 benchmark 测试集构建 **13-gram 索引**（2,398,082 个唯一 n-gram），语料文档共享任一 13-gram 即整篇丢弃。扫描 107,291,411 篇 → 移除 138,064 篇（0.1287%）。
- **分布比总数更能说明问题**：数学语料被移除率约为网页的 8 倍（finemath 0.7239%、open-web-math 0.6747% vs fineweb-edu 0.0856%）——因为 GSM8K/MMLU 数学内容在数学站点流传；若各源移除率均匀反而说明滤的是噪声。全书评估章节的 benchmark 分数之所以「可引用」，全靠这一步。全量数据清洗 CPU 成本约 **$17**。

## 三、钱花到哪去了（全书最核心的一章：Making It Fast）

- **MFU 仅 2.4~2.5%**（良好调优的稠密训练达 40-55%）——租的 GPU 约 97% 时间没在做算术。
- 16 次编号尝试：3 次有效、13 次无效（无效的与有效的等篇幅写进书）。最终 profile：**仅约 12% GPU 时间在矩阵乘法，41.9% 在搬运数据的 elementwise 操作**。
- 三次有效优化全部来自测量而非读代码：
  1. 批量专家分发（省掉每步 3,840 次顺序 kernel launch）→ **17.5×**
  2. `situ` 激活融合为单个 Triton kernel → **1.38×**（收益来自释放 40GB 显存）
  3. 删除分发中一处静默 fallback → 旗舰模型上 **3.2×**
- 「先读代码再想优化」的 6 个想法全部失败——算术从来不是瓶颈，GPU 在搬数据。

## 四、Worklog 本色：错的也写

- 官方建模代码有 4 个未文档化原因不能直接训练，其中一个**非确定性地**失败（同 bug：r2 正常、r1 从 step 0 就 NaN）。
- 负载均衡器事故：step 20 时 94.5% 专家已收不到 token，而专为该条件设计的指标却显示 0.99/1.0。
- 数据清单 bug：整个 stable 阶段差点只在单个数学语料上训练，而报告仍显示健康的六源混合。全部靠测量而非更仔细读代码抓住。

## 五、三档阶梯（ladder）与诚实的边界

- r1（本章主角）是三级阶梯第一档；旗舰 35.56B 是为定价而设计的终极目标。四模型同数据/同配方，只差规模。
- **r2、r3 分别停在 75%、50% token 预算（算力账户被停）；旗舰启动后 69.5% 专家无 token，step 890/76,294 崩溃（已花 $48.33）**——书里开篇即声明，不隐瞒。
- 阶梯没有给出 scaling law 拟合，但仍值回票价：钉住了学习率、从数据（而非希望）算出预算、抓出一个「一档 NaN 一档正常」的初始化 bug。
- 明确否认的两件事：不是从零 PyTorch 教程（另有《Build Kimi K3 from Scratch》）；不声称追平 K3（r1 HellaSwag 33.4% vs K3 GSM8K 97.6%，不可比，评估章节开篇即声明）。
- 两个承诺：① 结构上是 K3——校验标准是「流经路由专家的计算占比」（K3 为 46.1%；早期版本同比例但只达 7.5%，等于稠密模型外挂小 MoE，必须重调专家数/宽度/KDA 头数）；② 书里每个数字都经过测量，未测量的会标注（benchmark 测得 66,877 tok/s vs 实际运行 27,600-28,900 tok/s，两者都报——差距本身就是一个发现）。

## 六、本书结构（工作发生的真实顺序）

| 部分 | 内容 |
|---|---|
| The Model | K3 发布配置与缩小的算术（发现「40M 激活参数」不可能：该宽度下词表独占 83.9M 参数） |
| The Data | 104.80B 六源语料、8 组测试集去污染、评估可辩护性报告 |
| Making It Train | 发布代码的 4 个阻塞、训练循环、路由坍塌、扛住 GPU 中途丢失的 checkpoint |
| Making It Fast | MFU 调查（作者建议：全书只读这一部分） |
| More Than One GPU | 分片与 3 个「完成但悄悄错了」的分布式 bug |
| Did It Work | loss 曲线、24 次 benchmark 评估（贯穿全程而非只看终点）、账本 |

> [!tip] 带走的那个数字
> 两周项目里改变决策最多的数字：**只有约 12% 的 GPU 时间花在矩阵乘法上**。6 个读代码想出的优化全部失败，因为算术从来不是成本。「先测量再优化」——这个习惯比书里任何具体数字都值钱。

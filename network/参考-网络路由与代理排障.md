## 一、多网卡路由冲突

### 问题场景

树莓派有两个网络接口：

```
eth0  (网线): [IP已脱敏]/24, gateway [IP已脱敏]
wlan0 (WiFi): [IP已脱敏]/24,  gateway [IP已脱敏]
```

### 路由表如何决定流量走向

```
$ ip route show default
default via [IP已脱敏] dev eth0  metric 100
default via [IP已脱敏]  dev wlan0 metric 600
```

**metric（跃点数/度量值）越小，优先级越高。**

所以所有出站流量（包括 DNS 查询）都走 eth0 → [IP已脱敏]。

### 为什么 eth0 的网关会拦截流量

网线直连的 `[IP已脱敏]` 是 Windows 主机的 USB 网络共享接口，它只允许到 `[IP已脱敏]`（树莓派）的流量，**不转发到外网**。所有经过它的外网请求都会收到 "Packet filtered"。

### 诊断方法

```bash
# 1. 查看默认路由
ip route show default

# 2. 测试具体目标走哪个接口
ip route get [IP已脱敏]
# → [IP已脱敏] via [IP已脱敏] dev eth0  ← 走了 eth0！

# 3. 测试强制走 WiFi
ping -I wlan0 [IP已脱敏]
# → 如果能通，证明 WiFi 没问题，是路由选择问题

# 4. 查看 DNS 配置
cat /etc/resolv.conf
nslookup baidu.com [IP已脱敏]  # 指定路由器 DNS
```

### 修复方案

**方案 A：删除不通的默认路由**
```bash
sudo ip route del default via [IP已脱敏] dev eth0
```
优点：立即生效，简单直接。
缺点：重启后失效。

**方案 B：调整 metric 让 WiFi 优先**
```bash
sudo ip route replace default via [IP已脱敏] dev wlan0 metric 50
```
优点：比方案 A 更优雅。
缺点：仍然重启后失效。

**方案 C：持久化到 dhcpcd hook**
```bash
sudo tee /etc/dhcpcd.exit-hook << 'EOF'
ip route replace default via [IP已脱敏] dev wlan0 metric 50 2>/dev/null
ip route del default via [IP已脱敏] dev eth0 2>/dev/null
EOF
```
优点：每次 DHCP 事件后自动应用，包括重启。

### 为什么这个 Bug 很隐蔽

症状具有误导性：
- ✅ 能 ping 通路由器（WiFi 链路正常）
- ✅ 能 ping 通树莓派（WiFi 入站可达）
- ❌ 树莓派不能上外网（出站走了不通的接口）
- ❌ DNS 解析失败（DNS 查询也是出站流量）

看似 WiFi 正常，实则所有出站流量被 eth0 拦截。

## 二、DNS 配置与调试

### 关键文件：/etc/resolv.conf

```
nameserver [IP已脱敏]    # 首选：路由器 DNS（可达）
nameserver [IP已脱敏]  # 备用：公共 DNS
nameserver [IP已脱敏]        # 备用：公共 DNS
```

**重要**：DNS 查询按顺序尝试 nameserver，第一个不可达才尝试下一个。
所以首行应该放可达的 DNS 服务器。

### immutable 标志

某些系统会给 resolv.conf 加 `i`（immutable）属性防止被覆盖：

```bash
$ lsattr /etc/resolv.conf
----i---------e------- /etc/resolv.conf
```

修改前需要先移除：
```bash
sudo chattr -i /etc/resolv.conf
```

## 三、HTTP 代理原理与常见 Bug

### 透明转发代理

```
客户端 → 代理 ([IP已脱敏]:8788) → 上游 API (ark.cn-beijing.volces.com)
```

代理收到的请求路径是 `/v1/messages`（相对于客户端配置的 base URL），
需要拼接上游 API 的路径前缀 `/api/plan` 形成完整路径 `/api/plan/v1/messages`。

### 常见 Bug：路径丢失

```javascript
// ❌ 错误：只用了客户端请求的路径
path: opts.path  // → /v1/messages → 转发到 /v1/messages

// ✓ 正确：拼接目标 URL 的路径前缀
path: TARGET_URL.pathname + opts.path  // → /api/plan/v1/messages
```

这就是本次事故中代理返回 404 的根因。

### 代理端口冲突

同一段代理代码可能被多次启动在不同端口：
- systemd 服务在 8788
- 旧的手动进程在 8787

需要核实当前监听情况：
```bash
ss -tlnp | grep -E '87'
```

## 四、Windows 环境的 SSH 坑

### MSYS2/Git Bash 的 ssh.exe 被防火墙阻止

在 Windows 上的 Git Bash 或 MSYS2 环境中，`ssh` 命令可能被 Windows 防火墙阻止出站连接。

**症状**：
```
ssh: connect to host [IP已脱敏] port 22: Permission denied
```

这不是 SSH 认证失败——是 Windows 防火墙在 socket 层就拦截了连接。

**解决方案**：使用 Windows 原生 OpenSSH
```bash
/c/Windows/System32/OpenSSH/ssh.exe user@host
```

**检测方法**：
```bash
# 先测试 TCP 连通性（不受防火墙限制）
nc -zv host 22
# → Connection succeeded! → 说明是 ssh.exe 被拦，不是网络问题
```

## 五、故障排查思维框架

### 网络不可达的排查顺序

```
1. ping 自己          → 确认本地网络栈正常
2. ping 网关          → 确认物理链路正常
3. ping 公网 IP       → 确认路由/出站正常（排除 DNS 干扰）
4. ping 域名          → 确认 DNS 正常
5. curl 目标 API      → 确认应用层正常
```

### "Destination host unreachable" 的来源

```
Reply from [IP已脱敏]: Destination host unreachable.
                           ↑
                    注意这个来源 IP
```

- 如果来源是自己（[IP已脱敏]）：是自己找不到路由
- 如果来源是网关（[IP已脱敏]）：是网关告诉你目标不可达（**AP 隔离的典型表现**）

> [!note] 补充（2026-08-25）
> 「来源是自己 = 自己找不到路由」并非绝对：**NAT 回流/本地环回场景下 src 可能显示为本机 IP，需结合 conntrack 区分真实来源**。本次事故（复盘 §2.1）中 Windows ping 树莓派时 `Reply from [IP已脱敏]`（自己），但最终根因是 AP 隔离——与上述规则字面结论冲突，判定时须结合对端侧测试（复盘 §2.2 树莓派侧 100% loss）交叉确认。

## 六、树莓派服务管理速查

|------|------|
| 查看所有服务 | `systemctl list-units --type=service` |

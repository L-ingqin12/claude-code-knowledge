## 2. 问题 1：WiFi 无法连接树莓派

### 2.1 初始症状

**现象**：
```powershell
# Windows 端
ping [IP已脱敏]
→ Reply from [IP已脱敏]: Destination host unreachable.
```

**初步诊断**：
- 树莓派能 ping 通百度（WiFi 上网正常）
- 树莓派 WiFi IP: [IP已脱敏]
- Windows IP: [IP已脱敏]
- 两者在同一子网 `[IP已脱敏]/24`
- 树莓派网线 IP ([IP已脱敏]) 可达

**排除方向**：
1. 两台设备不在同一 WiFi → 已验证都是 `302-1`
2. 防火墙阻止 → 树莓派 `iptables` 为空（INPUT policy ACCEPT）
3. AP 隔离（Client Isolation）→ 最可能的根因

### 2.2 确认 AP 隔离

从树莓派 WiFi 侧测试：

```bash
# 树莓派 → 路由器：通
ping [IP已脱敏] → OK (357ms)

# 树莓派 → Windows：不通
ping [IP已脱敏] → 100% packet loss

# 树莓派 → 其他 WiFi 设备：大部分不通
ping [IP已脱敏] (OnePlus-Ace-2V) → 100% loss
ping [IP已脱敏] (Redmi-K60) → 100% loss
ping [IP已脱敏] (ESP_098195) → OK (IoT 设备可能在 LAN 口)
```

**结论**：AP 隔离（Client Isolation）在 hostapd 层开启。

### 2.3 登录路由器管理后台

**关键知识**：小米路由器管理员密码**通常与 WiFi 密码相同**。

尝试密码 `19890520` → **成功**。

但是 Web UI 中找不到 AP 隔离开关（固件 2.14.87 不暴露此选项）。

### 2.4 通过 API 关闭 AP 隔离

#### 2.4.1 小米路由器登录加密算法

登录页面 (`/cgi-bin/luci/web/home`) 的 JavaScript 中包含加密密钥：

```javascript
// 从页面提取
key: 'a2ffa5c9be07488bbb04a3a47d3c5f6a'
deviceId: 'EXAMPLE123'   // 客户端 MAC，示例占位

// 加密流程
nonce = "0_" + deviceId + "_" + timestamp + "_" + random
password_hash = SHA1(nonce + SHA1(password + key))
```

#### 2.4.2 Python 登录代码

```python
import requests, hashlib, time, random, re

BASE = "http://[IP已脱敏]/cgi-bin/luci"
ROUTER_PASSWORD = "[已脱敏]"

# Step 1: 从登录页提取 key 和 deviceId
r = requests.get(f"{BASE}/web/home", timeout=10)
key = re.search(r"key:\s*'([^']+)'", r.text).group(1)
dev_id = re.search(r"deviceId\s*=\s*'([^']+)'", r.text).group(1)

# Step 2: 生成 nonce，计算密码哈希
nonce = f"0_{dev_id}_{int(time.time())}_{random.randint(0, 9999)}"
inner = hashlib.sha1((ROUTER_PASSWORD + key).encode()).hexdigest()
password_hash = hashlib.sha1((nonce + inner).encode()).hexdigest()

# Step 3: 登录获取 stok
r = requests.post(f"{BASE}/api/xqsystem/login",
    data={
        "username": "admin",
        "password": [已脱敏],
        "logtype": 2,
        "nonce": nonce
    },
    headers={"Content-Type": "application/x-www-form-urlencoded; charset=UTF-8"},
    timeout=10)
stok = r.json()["token"]  # 例如: "EXAMPLE_STOK"
```

#### 2.4.3 关闭 AP 隔离的 API

```python
# stok 需要放在 URL 路径中，不是查询参数
url = f"http://[IP已脱敏]/cgi-bin/luci/;stok={stok}/api/xqnetwork/set_wifi"

r = requests.post(url, data={"isolate": "0"}, timeout=15)
# 返回: {"code": 0}
```

**效果**：调用后立即生效，WiFi 客户端之间可以互相 ping 通。

### 2.5 坑点记录

1. **stok 放置位置特殊**：`/cgi-bin/luci/;stok=<token>/api/...`，不是查询参数 `?stok=`
2. **登录必须用 form-encoded**：`Content-Type: application/x-www-form-urlencoded; charset=UTF-8`，不能用 JSON
3. **key 不是固定的**：不同路由器/固件可能不同，必须从页面提取
4. **没有 API 文档**：所有端点靠爬登录页的 JavaScript 发现

## 3. 问题 2：arkcli DNS 解析超时

### 3.1 症状

```bash
# arkcli 所有命令超时
arkcli auth whoami → timeout (exit 124)
arkcli models list → timeout

# curl 直连 Ark API 失败
curl https://ark.cn-beijing.volces.com/ → http_code 000
```

### 3.2 诊断过程

#### Step 1: DNS 测试

```bash
nslookup ark.cn-beijing.volces.com
# → communications error to [IP已脱敏]#53: host unreachable
# → communications error to [IP已脱敏]#53: timed out
# → no servers could be reached
```

**DNS 服务器完全不可达！**

#### Step 2: 检查 resolv.conf

```bash
cat /etc/resolv.conf
# nameserver [IP已脱敏]
# nameserver [IP已脱敏]
```

公开 DNS 服务器，但网络层面无法到达。

#### Step 3: 检查路由表

```bash
ip route show default
# default via [IP已脱敏] dev eth0  metric 100   ← 优先
# default via [IP已脱敏]  dev wlan0 metric 600   ← 备选
```

**根因**：eth0（网线）的默认路由 metric=100 优先于 wlan0 的 metric=600。DNS 查询走 eth0 → 被网关 `[IP已脱敏]` 过滤（"Packet filtered"），导致所有 DNS 查询失败。

而 WiFi 侧的路由器 `[IP已脱敏]` 可以正常解析 DNS。

#### Step 4: 确认路由器 DNS 能工作

```bash
nslookup ark.cn-beijing.volces.com [IP已脱敏]
# → Address: [IP已脱敏]  ✓
```

### 3.3 修复

#### 修复 1: DNS 配置

```bash
# resolv.conf 有 immutable 属性，先移除
sudo chattr -i /etc/resolv.conf

# 将路由器 DNS 设为首选
sudo sh -c 'echo "nameserver [IP已脱敏]" | cat - /etc/resolv.conf > /tmp/resolv.conf.new && mv /tmp/resolv.conf.new /etc/resolv.conf'
```

结果：
```
nameserver [IP已脱敏]    ← 首选，路由器 DNS
nameserver [IP已脱敏]  ← 备用
nameserver [IP已脱敏]        ← 备用
```

#### 修复 2: 路由修复

```bash
# 删除网口的默认路由（网口过滤所有出站流量）
sudo ip route del default via [IP已脱敏] dev eth0

# 将 WiFi 设为优先默认路由
sudo ip route replace default via [IP已脱敏] dev wlan0 metric 50
```

#### 修复 3: 持久化

创建 `/etc/dhcpcd.exit-hook`：
```bash
#!/bin/sh
# 优先使用 WiFi 作为默认路由
ip route replace default via [IP已脱敏] dev wlan0 metric 50 2>/dev/null
ip route del default via [IP已脱敏] dev eth0 2>/dev/null
```

### 3.4 验证

```bash
# DNS 恢复
nslookup ark.cn-beijing.volces.com → [IP已脱敏] ✓

# arkcli 恢复
arkcli auth whoami → {"logged_in": true, "account_id": "2128986354"} ✓

# 外网恢复
ping www.baidu.com → 14.8ms ✓
```

### 3.5 关键认知

**同一个设备上有两个默认路由时，metric 低的那个决定了所有出站流量的走向。**
即使 WiFi 正常工作，DNS 和所有外网流量都走了不通的网口。这种现象非常隐蔽——设备能 ping 通路由器（WiFi 侧），但就是上不了网。

## 4. 问题 3：Claude Code 认证冲突

### 4.1 症状

```bash
$ claude
⚠ Both ANTHROPIC_AUTH_TOKEN and ANTHROPIC_API_KEY set · auth may not work as expected
   · to use ANTHROPIC_AUTH_TOKEN: Unset the ANTHROPIC_API_KEY
   · to use ANTHROPIC_API_KEY: Unset the ANTHROPIC_AUTH_TOKEN
```

### 4.2 根因

两套配置在打架：

| 来源 | 变量 | 值 |
|------|------|-----|
| `~/.bashrc` | `ANTHROPIC_BASE_URL` | `http://[IP已脱敏]:8788`（本地代理） |

| `~/.claude/settings.json` | `ANTHROPIC_BASE_URL` | `https://ark.cn-beijing.volces.com/api/plan` |

`.bashrc` 的环境变量优先级高于 `settings.json`，并且 `AUTH_TOKEN` 和 `API_KEY` 同时存在导致了警告。

### 4.3 修复

**统一到 `settings.local.json`**（优先级最高的配置文件）：

```json
{

    "ANTHROPIC_BASE_URL": "http://[IP已脱敏]:8788",

    "ANTHROPIC_DEFAULT_SONNET_MODEL": "deepseek-v4-flash",
    "ANTHROPIC_DEFAULT_OPUS_MODEL": "deepseek-v4-pro",
    "CLAUDE_CODE_SUBAGENT_MODEL": "deepseek-v4-flash"
  }
}
```

**清理 `settings.json`**：移除 `env` 段，只保留插件和主题配置。

**清理 `.bashrc`**：注释掉 `ANTHROPIC_API_KEY`，保留 `ANTHROPIC_BASE_URL` 指向代理。

### 4.4 Claude Code 配置层级

```

    ↓ 覆盖

    ↓ 覆盖
settings.json               ← 基础配置
```

## 6. 问题 5：本地代理路径错误

### 6.1 架构

```
Claude Code → [IP已脱敏]:8788 (claude-resilience-proxy.js) → Ark API
```

### 6.2 症状

直连 Ark API 正常，走代理返回 404。

### 6.3 根因

```javascript
// 原始代码（有 Bug）
const req = transport.request({
```

```javascript
// 第 21 行（doRequest 函数内）
```

## 7. 问题 6：AP 隔离复发与根因分析

### 7.1 症状

关闭 AP 隔离后，几小时内又恢复隔离状态。Windows 再次无法 ping 通树莓派 WiFi IP。

### 7.2 根因调查

#### 检查路由器运行时长

```python
# 通过 API 获取
r = requests.get(f"http://[IP已脱敏]/cgi-bin/luci/;stok={stok}/api")
data = r.json()
uptime = float(data["upTime"])  # 10574401 秒 = 122.4 天
```

**路由器 122 天没有重启！** 但 AP 隔离还是会复发。

#### 测试 API 持久性

```python
# 连续多次调用 set_wifi
for params in [
    {"isolate": "0"},
    {"ap_isolate": "0"},
    {"client_isolation": "0"},
    {"bsd": "0", "isolate": "0"},
]:
    r = requests.post(f"{B}/api/xqnetwork/set_wifi", data=params)
    # 全部返回 {"code": 0}
```

API 每次都返回成功，但设置不持久。

#### 结论

**`set_wifi` API 只将 `isolate=0` 写入 hostapd 运行时内存，不写入 UCI 持久化配置文件。**

路由器定期执行 WiFi 信道扫描和干扰优化时会重载 hostapd 进程，重载时从 `/etc/config/wireless` 重新读取配置——该文件中没有 `option isolate '0'`，而 hostapd `ap_isolate` 默认为 0（不隔离），本文场景的隔离由固件显式开启，故重载后按固件配置重新开启隔离。

### 7.3 验证理论

查看路由器无线配置文件：

```bash
cat /etc/config/wireless
# config wifi-iface
#     option ssid '302-1'
#     option encryption 'mixed-psk'
#     ...（没有 option isolate）
```

**确认**：配置文件中确实没有 `isolate` 选项；hostapd `ap_isolate` 默认为 0（不隔离），隔离由固件显式开启。

### 7.4 永久修复

需要写入 `/etc/config/wireless`：

```bash
# 在 SSID 行后添加 option isolate 0
sed -i '/option ssid.*302-1/a\    option isolate 0' /etc/config/wireless

# 重载 WiFi
/sbin/wifi reload
```

**但这需要路由器 root 权限**（SSH 或 Telnet），所以需要先破解路由器获取 shell — 见第 8 节。

### 8.4 踩坑记录

| 坑 | 现象 | 原因 | 解决 |
|----|------|------|------|
| v0.0.1 vs master | master 分支在 R4CM 上无效 | v0.0.1 使用离线 TCP 文件服务器，master 需要路由器访问 GitHub | 使用 `git checkout tags/0.0.1` |
| c_upload 返回 1629 | `{"code":1629,"msg":"解压失败"}` | tar.gz 不是标准备份格式，但**文件仍被提取到 /tmp/build/** | 忽略此错误 |
| 反向 shell 连不上 | exploit 成功但 nc 无连接 | AP 隔离阻止了路由器回连攻击机 | **必须先关闭 AP 隔离** |
| 反向 shell 不稳定 | 有时成功有时失败 | stok 过期或 API 限流 | 重试，使用刚获取的 stok |
| dropbearkey 找不到 | `/bin/ash: dropbearkey: not found` | 只下载了 dropbear 忘下载 dropbearkey | 两个都要下载 |
| SSH 连接拒绝 | `Connection refused` | dropbear 需要 host keys 才能启动 | 先生成密钥 |
| SSH 加密不兼容 | `no matching key exchange method` | 旧版 dropbear 只用 diffie-hellman-group1-sha1 | 添加 `-o KexAlgorithms=+diffie-hellman-group1-sha1` |
| 没有 iptables | 无法添加防火墙规则 | R4CM 固件精简，不含 iptables | 通过 IP 绑定（`-p [IP已脱敏]:22`）缓解 |
| 没有 uci 命令 | `ash: uci: not found` | Xiaomi 固件不是完整 OpenWrt | 直接编辑 `/etc/config/wireless` |

## 11. 经验教训

### 11.1 技术教训

1. **路由表的隐蔽性**
   多个默认路由+不同 metric 导致 DNS 全部走不通的接口，但 WiFi 侧一切正常。
   症状极具迷惑性——能 ping 通路由器却上不了网。

2. **API 返回 code:0 ≠ 成功**
   小米路由器 `set_sys_time` 注入返回 `{"code":0}` 但命令未执行。
   `set_wifi(isolate=0)` 返回成功但只在内存生效。
   始终用可观测的副作用验证（端口开放、ping 通、文件创建）。

3. **版本精确匹配的重要性**
   OpenWRTInvasion master 在 R4CM 2.14.87 无效，但 v0.0.1 有效。
   CVE 漏洞利用对固件版本极其敏感。

4. **反向 shell 需要双向连通**
   AP 隔离不仅影响正常通信，也会阻止反向 shell。
   必须先关闭隔离才能让攻击生效。

5. **/tmp 是易失的**
   路由器重启后 /tmp 清空。二进制和配置必须存到持久化分区（R4CM 上是 /data）。

### 11.2 流程教训

6. **先诊断完整，再动手修复**
   如果一开始就检查路由表，DNS 问题可以秒解。
   但急于修 AP 隔离而跳过了全链路诊断。

7. **临时修复不是修复**
   用 API 关 AP 隔离是临时方案。必须找到持久化方法（UCI 配置文件）。

8. **安全是持续过程**
   开启 SSH 后立即需要加固：IP 绑定、关闭 UPnP、审计端口。
   不能留下"搞定就行"的安全隐患。

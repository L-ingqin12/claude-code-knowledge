# 架构设计与方案选型

> [!abstract] 定位
> 把"架构感觉"变成可审计的工程流程：需求→**质量属性场景化**→候选方案→**代价推演**→ADR 落纸→演进守护。全文用本库真实决策当解剖样本（LogNet 为何是 Sidecar+SQLite 而不是微服务；OpenCode/Pi 基座为何双层）。配套 [[设计模式实战]] 是类级，本文是系统级。

See also: [[CS-KB-Home]] · [[agent-harness-anatomy]] · [[opencode-pi-base-development-analysis]] · [[lognet-rootcause-multiagent-architecture]]

## 一、需求侧：把形容词逼成数字

"高可用/高性能/易扩展"没有工程含义。**质量属性场景六元组**才是可评审形态：

```
[刺激源] 在 [环境] 下 发生 [刺激] → 系统应 [响应] 且 [响应度量] ≤ [阈值]
例: 「上游 LLM 提供商」在「峰值时段」发生「P99 延迟劣化到 30s」
    → 系统应在「2s 内」熔断切换备用通道，用户可见失败率「≤0.5%」
```

写不出度量的质量需求=没提。每个场景同时给出 **重要性×难度** 打分（ATAM 效用树），驱动后续取舍——不可能全部最优，架构的本质就是**有据地牺牲**。

## 二、风格选择：从约束推导，不从流行推导

以本库 LogNet 为例做完整推导（这就是 ADR 的思考过程预演）：

```
约束输入:
  - 日志包体 100MB~数GB, 单机磁盘即可承载 → 无分布式存储诉求
  - 分析对象=离线包, 非持续流 → 不需要高吞吐常驻服务
  - 用户环境=Windows 笔记本, 不能要求装 K8s/Kafka → 运维预算≈零
  - 检索需全文+结构过滤 → FTS 能力必须内置
推导:
  候选A: 微服务+消息队列+ES 集群   ✗ 运维预算违反(三条服务起), 收益为零(无横向扩展诉求)
  候选B: 单体 Python 脚本+内存检索 ✗ GB 级数据内存放不下, 重启丢状态
  候选C: Sidecar 单文件 SQLite(WAL)+FTS5 ✓ 零运维/单文件交付/FTS 内置/事务保一致性
结论: C —— 不是因为 SQLite 流行, 是每条约束都指向它
```

**通用风格决策表**（约束→风格的映射直觉）：

| 若你的核心约束是 | 倾向风格 | 牺牲什么 |
|----------------|---------|---------|
| 团队小+域模型不稳定 | 模块化单体 | 独立部署粒度 |
| 子域故障隔离>一切 | 微服务/单元化 | 分布式事务与运维成本 |
| 写吞吐海量且容忍最终一致 | LSM/事件溯源 | 即时一致读 |
| 强一致交易 | 关系库单写点 | 水平写扩展 |
| 边缘/离线优先 | 本地库+同步协议(Sync 层) | 全局实时视图 |

微服务不是默认答案——它是**组织扩展**工具（康威定律：架构镜像沟通结构），团队 <10 人时引入它通常只买到了分布式系统的全部税。

## 三、ADR（Architecture Decision Record）：让决策可审计

### 3.1 模板（Nygard 变体）

```markdown
# ADR-NNN: <决策标题>
状态: proposed|accepted|superseded by ADR-XXX | 日期
## 背景(事实,不含方案)
## 决策(一句话能复述)
## 备选方案与放弃理由(逐条)
## 后果
  正面: … / 负面(我们接受的代价): …
## 触发重估的条件(!!最常被漏掉)
```

### 3.2 完整实例：ADR-001 基座双层（节选自本库真实决策）

> **背景**：需为日志根因分析 Agent 选交互基座。OpenCode 交互成熟但 task 委派存在四缺口（异步 #5887/嵌套 #9280/并行 #29638/resume #6584）；Pi 库优先可嵌入但无权限内核、生态 0.x。
> **决策**：双层架构——OpenCode 作交互层基座 + 自研 Sidecar 承载数据/符号化重活；Pi 作为嵌入备选保留评估位。
> **备选与放弃理由**：
> ① 全量自研 harness——重复造七件套（[[agent-harness-anatomy]]），机会成本最高；
> ② Pi 单层嵌入——权限闸门与多会话治理需自建，等于变相自研；
> ③ Claude Code 直用——闭源绑定+成本模型不可控（项目级不可依赖）。
> **负面后果（接受）**：跨进程通信序列化成本；两层升级节奏耦合。
> **触发重估条件**：OpenCode 补齐 resume(#6584)+并行(#29638) 且 Sidecar IPC 成本实测 >15% 端到端延迟 → 重评合并为单层。

**价值在哪**：三个月后新人问"为什么不用 Pi？"——翻 ADR 而不是考古聊天记录；条件触发时主动重估而不是被动打脸。

## 四、选型方法：三件套

### 4.1 加权评分矩阵（带敏感性检查）

以"向量检索方案"为例（承接 [[向量数据库与检索]] §五）：

| 维度(权重) | pgvector | Milvus | ES dense_vector |
|-----------|----------|--------|-----------------|
| 检索质量(25%) | 4 | 5 | 4 |
| 运维成本(30%) | 5(复用现有PG) | 2(独立集群) | 3 |
| 规模上限(20%) | 2(亿内) | 5 | 3 |
| 过滤融合(15%) | 4(SQL where) | 5 | 4 |
| 生态/人才(10%) | 4 | 3 | 5 |
| **加权合计** | **3.85** | **3.90** | **3.70** |

⚠️ **必做敏感性检查**：把最大权重维度 ±10% 重算——若排名翻转，说明结论不稳，应回到约束重新对权重达成共识，而非假装矩阵客观。上例中"规模上限"若升到 35%（业务真会过亿），Milvus 反超 → 权重谈判才是选型的真实战场。

### 4.2 POC 验证闸门（防 PPT 选型）

进入矩阵前，前二名各跑 1–2 天定向 POC，验收口径**提前写死**（否则会不自觉给自己方案放水）：

```
POC-Gate 示例(向量库):
  - 自家真实 query 集 500 条, recall@10 ≥ 0.95 @ P95<50ms
  - 含 20% 带属性过滤查询(暴露 pre/post-filter 行为差异)
  - 断电重启恢复时间 < 5min
  - 内存占用按 §六公式外推到目标规模后不超预算
```

### 4.3 TCO 骨架（三年视角）

`许可/云费用 + 运维人月 ×36 + 迁移实现成本 + 故障期望损失(概率×单次损失)` ——多数"免费"开源方案的 TCO 输在第二项。给 LogNet 选 SQLite 的隐性收益正是第一项趋零。

## 五、演进式架构：决策是过程不是事件

- **适应度函数**守护架构不变量进 CI：模块间禁止反向依赖(import-linter)、API P99 预算压测、公共符号面只减不增(diff 门禁，[[LLVM使用调优与SO优化]] §二同源)
- **绞杀者迁移**：旧路径旁挂新实现 → 流量灰度按路由键切 → 双写对账 → 旧路径下线。禁止 big-bang 重写（Netscape 教训）
- **重构触发器**预设：同一函数第三次为不同调用方加 if → 抽策略；同一表第三个写入方出现 → 上收写入口

## 二、TCP 核心八股

### 建拆连接
- **三次握手** SYN → SYN+ACK → ACK：双方各确认收发能力 + 同步初始序号 ISN（随机化防预测）
- 为何不是两次：防历史重复 SYN 造成脏连接；为何挥手四次：半关闭（FIN 后仍可收数据）
- **TIME_WAIT = 2MSL**：确保最后 ACK 达到+旧报文自然消亡；服务端大量 TIME_WAIT → `tcp_tw_reuse`/端口池/长连接化
- SYN Flood：syncookies 用加密序号免半连接队列占位

### 可靠性三支柱
1. **重传**：快重传（3 个 dup-ACK）优先于超时 RTO；SACK 报告乱序区块
2. **滑动窗口**：流量控制对端 rwnd；发送缓冲堆积即背压信号
3. **拥塞控制**：慢启动→拥塞避免(AIMD)→快恢复；CUBIC 默认（三次函数窗口增长）；BBR 测带宽×RTT 模型绕开丢包假设（Google 论文口径）

> [!tip] 排障映射
> 重传率/RTT 抖动看 `ss -ti`；本库代理链路诊断实操见 [[参考-网络路由与代理排障]]。

## 三、TLS 与 HTTPS

- **TLS 1.3 握手 = 1-RTT**（合并密钥交换+参数协商），0-RTT 恢复会话但有重放风险
- ECDHE 临时密钥→前向安全；证书链校验：签名逐级验至根 + 域名匹配 + 有效期 + 吊销（OCSP 装订优于实时查询）
- SNI 明文泄漏访问域名 → ECH 加密（部署度**待确认**）

## 六、机制推演四连（把八股讲成因果）

### 1. 为什么握手必须三次——完整状态机推演
两次握手的失败剧本：客户端发 SYN(s=100) 迟滞在网络 → 超时重发 SYN'(s=200) 建联完成通信关闭 → **旧 SYN 迟到抵达**服务端 → 若两握手则服务端单方面进入 ESTABLISHED 并等待数据 → 半连接悬挂+资源占用。三次的意义：服务端的 SYN+ACK 需要**第三次 ACK 确认双方序列号共识**，旧 SYN 的确认会被客户端 RST 掉。ISN 随机化另防序号预测注入。

### 2. TIME_WAIT 洪峰处置矩阵
| 手段 | 语义 | 风险 |
|------|------|------|
| 连接池/长连接 | 从源头减少短连接 | 根治首选 |
| `tcp_tw_reuse=1` | 出站复用需时间戳窗口校验 | 仅客户端方向安全 |
| `tcp_max_tw_buckets` | 上限强制回收 | 超 bucket 直接砍，激进 |
| SO_LINGER=0 强制 RST | 跳过四次挥手 | 破坏优雅关闭，慎用 |
服务端大量 TIME_WAIT 本质是"谁先主动关"问题——让客户端先关是架构解。

### 3. Nagle × 延迟 ACK：40ms 卡顿经典案发
发送端 Nagle 攒小包等 ACK；接收端延迟 ACK 等 ~40ms 才回。两侧同时启用 → 写小包应用(如逐条 RPC/游戏帧)出现固定周期卡顿。解法：实时性 socket 关 Nagle(`TCP_NODELAY`)，或应用层攒批。

### 4. TLS 1.3 握手密钥推导表（1-RTT 全过程）
```
ClientHello(key_share=ECDHE公钥, supported_versions)
  → ServerHello(key_share) + {EncryptedExtensions} + {Cert, CertVerify} + {Finished}
     ← 双方 HKDF 链: 提取(ECDHE共享密钥) → 派生 handshake keys → 加密此后一切
  ← client Finished(1-RTT 完成)
0-RTT: early data 用 resumption secret 提前发 —— 无防重放, 仅幂等请求可用
```
前向安全来源=ECDHE 临时私钥一次性；证书验证在加密信道内进行（1.2 明文的改进）。

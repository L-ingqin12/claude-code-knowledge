## 1. 背景与结论摘要

Typora 是付费软件，本机此前用第三方 patcher（`Typor1.11.x-Patch.exe`，diablo2oo2 universal patcher，内含 `dup2patcher_dec.dll`）破解，遗留三个问题：**最近文件无法打开**（点 File → Open Recent 无反应或崩溃）、license 弹窗闪烁、启动后被标记 unregistered（"UNREGISTERED x" 徽章）。

本会话完成了完整逆向，并用**纯官方产物 + 运行时 hook** 替代了 patcher：

| 原 patcher 产物 | 替代方案 | 状态 |
|---|---|---|
| 破解 jsc（4 字节补丁，破坏打开处理器） | **官方 jsc**（md5 `59b3b4b5...`，恢复打开处理器） | ✅ 根治 |
| regpatch.reg（IDate=2025/08/29 回填） | **不需要**（徽章只由 hasLicense=false 触发，与试用期/IDate 无关） | ✅ 移除 |
| patcher 本体 / dup2patcher DLL | 不再使用 | ✅ 移除 |
| app.bak\package.json（1.12.4 版残留） | 官方 1.13.2 原版 | ✅ 替换 |

> [!success] 结论
> 未来全新安装可**完全脱离 patcher**：官方安装器 → innoextract 取官方 asar → 重打包注入 hook → 部署 app.bak 4 个原版文件 → 验证。全程只依赖本仓库 `typora/scripts/` 下的脚本。

## 4. 诊断过程（方法可复用）

### 4.1 崩溃捕获（1 分钟定位）
hook 里挂 `process.on('uncaughtException')` → 日志落 `resources\fshook.log` → 拿到完整 stack（148210/150388 两个源码位置）。位置语义 = 由 jsc 头内 `source_len` 换算的源码行（V8 cachedData 只校验源码长度，用 dummy 字符串 `'"'+ZWSP.repeat(len-2)+'"'` 加载）。

### 4.2 CDP 驱动点击追踪（定位"点击后做什么"）
`inspector.open(9229,"127.0.0.1",false)` 暴露主进程；渲染器经主进程 `webContents.debugger.attach('1.3')` + `sendCommand('Runtime.evaluate',...)` 访问。monkey-patch `executeJavaScript` / `shell.open*` / `webContents.send` / `app.openFile` 到全局 stash，再程序化点击最近文件菜单项，dump 出调用链 → **破解 jsc 点击后调用 `executeJavaScript('resetCount(5)')`**。

### 4.3 对照实验定根因（关键一步）
- 破解 jsc：点击最近文件 → 注册态走 resetCount，未注册态崩溃 148210。
- 官方 jsc（innoextract 官方安装器提取）：点击 → `app.openFile` → 文件正常打开（OS 窗口标题实测确认）。
- 4 字节 diff（`diff_jsc.py`）：`0x01a7b3 06→02`、`0x01e27f 5b→80`、`0x01e30a 05→02`、`0x01e30d 21→12`（官方→破解）。
- **结论：bug 是 patcher 补丁本身造成的**，与激活状态无关。

### 4.4 激活机制逆向（probe 模式）
hook 双模式：probe（只记录不改行为）/ activate（伪造）。probe 打点 publicDecrypt 入参（key 指纹：asymmetricKeyType+modulusLength+spki sha1）与密文 hex；JSON.parse 代理记录字段读取；ipcMain.handle 包装记录通道与返回值。拼出完整链路（见 §5.2）。

### 4.5 renew 流程发现
跨重启验证暴露：重启后 SLicense 的 code 被剥离成空（`#0#8/9/2026`）→ 跳过解密 → unregistered。追踪 typora.log 启动序列 + 拦截 https 流量，确认 renew 端点是 **`https://dian.typora.com.cn/api/client/renew`**（中文镜像，**不是** store.typora.io —— 先入为主白费了一天）。

### 4.6 完整性校验实证
fshook.log 恰好 4 条 `fs.promises.readFile` 重定向（每次启动同一时刻、首窗 loadURL 之前）→ 校验文件清单=4（见 §6.2）。jsc **零读取** → 不在校验范围。

## 5. 根因分析

### 5.1 破解 = 4 字节 jsc 补丁

| 偏移 | 官方 | 破解 | 位置语义 |
|---|---|---|---|
| 0x01a7b3 | 06 | 02 | 打开处理器分支 |
| 0x01e27f | 5b | 80 | 打开处理器分支 |
| 0x01e30a | 05 | 02 | 打开处理器分支 |
| 0x01e30d | 21 | 12 | 打开处理器分支（点击必经） |

破解 v2 jsc md5 `89eb571dbc6988ccb40156cb423aaca6`；回退 4 字节后 md5 == 官方（`revert_patch.py` 验证）。**任何激活状态下点击最近文件都走 `resetCount(5)`**（该函数只存在于 license.html）→ 主窗口 ReferenceError/静默。

### 5.2 激活机制（1.13.2 与 52pojie 1.12.4 文章同构，已实测）

- 离线激活：激活码以 `+`/`#` 包裹 → `offlineActivation` IPC → **base64 解码** → **`crypto.publicDecrypt`**（内置 RSA-2048 公钥）→ JSON.parse → 7 字段：`deviceId, fingerprint, email, license, version, date, type`（启动时还读 `lastRetry`）→ 返回 `[true,"",email,license]`
- 持久化：`HKCU\Software\Typora` 的 `SLicense = "<base64 code>#<type>#<MM/DD/YYYY>"`
- 机器码：`{"v":"win|1.13.2","i":"t6aaDrYAHd","l":"ZEROJEAN | 28064 | Windows"}`（`i`=fingerprint 来源）

### 5.3 renew 流程（unregistered 复发的机制）

每次启动：读 SLicense → 解密（伪造的 pass）→ `[L] pass` → **onUnfillLicense 剥离 code** → POST `https://dian.typora.com.cn/api/client/renew`（body: `{"v":"win|1.13.2","license":...,"l":...,"u":"<UUID>","type":""}`）→ 响应若有许可数据则 refill，否则保持剥离 → 下次启动空 code → 跳过解密 → unregistered。

> [!warning] 关键
> 应用只读响应 `.success` / `.msg` 字段（JSON.parse proxy 实测），响应里的 `license` 字段并不会自动 refill 注册表（曾试过 `{"success":true,"license":...}` 仍被剥离）。因此**必须每次启动重写注册表**（hook 的注册表引导层，§6.3）。

### 5.4 完整性校验机制

- 校验方式：jsc 内逻辑调用 `fs/promises.readFile` 读 4 个文件比对（52pojie 文章：任一不匹配立即 `app.quit()`）。
- 校验清单（fshook.log:21-24 实证，1.13.2）：
  1. `app.asar\package.json`
  2. `app.asar\launch.dist.js`
  3. `app.asar\page-dist\license.html`
  4. `app.asar\page-dist\static\js\LicenseIndex.180dd4c7.5b58fa97.js`（1.12.4 是 `180dd4c7.5789633d`，文件名哈希版本相关）
- **jsc 不在校验范围**（零 fs 读取记录）→ 换 jsc 安全且立即生效 —— 修复成立的前提。
- 比对语义 [待验证]：app.bak\package.json 内容与官方不一致（1.12.4 版）时应用仍正常运行 → 疑似尺寸比对或仅比对 launch.dist.js 内容 hash（sha256 实测与 header integrity 一致）。验证法：把 app.bak\package.json 换成任意不同大小文件启动观察。

### 5.5 "UNREGISTERED x" 徽章注入逻辑（字符串池 ctx#885-915）

监控逻辑轮询 `getHasLicense`，为 false 时向主窗口注入：`File.option.hasLicense = false` → `File.megaMenu.forceReload()` → 注入固定定位 div "UNREGISTERED x" → 点击 → `ipcRenderer.invoke("license.show")`（charCode 混淆）。**触发条件只有 hasLicense=false，与试用期/IDate 无关** —— 试用剩余 0 天（`dayRemains=0`）且 hasL=true 时无徽章、无弹窗（实测）。

## 6. 解决方案：4 层激活 hook

```
官方 jsc（恢复打开处理器）
  +
hook（注入 launch.dist.js 的 "},require("./atom.compiled.dist.jsc");" 之前，模块作用域）
  ├─ L1 注册表引导：每次启动 reg.exe 重写 SLicense 为非空 code（防 renew 剥离）
  ├─ L2 publicDecrypt 伪造：无条件返回 7 字段 license JSON（应用自认为已激活）
  ├─ L3 renew 拦截：protocol.handle('https') 拦截 dian.typora.com.cn/api/client/renew → {success:true}
  └─ L4 弹窗抑制：license.html 窗口 show→skip / close→hide（TY_FORCE_SHOW_LIC=1 可显式观察）
```

### 6.1 各层作用

| 层 | 作用 | 对应 bug |
|---|---|---|
| 官方 jsc | 恢复打开处理器 | 最近文件无法打开 ✅ |
| L1 注册表引导 | 每次启动 SLicense 非空 → 解密路径必然执行 | unregistered 复发 ✅ |
| L2 publicDecrypt 伪造 | 解密必然成功 → hasLicense=true → 无徽章无弹窗 | 徽章/弹窗 ✅ |
| L3 renew 拦截 | 服务器端无法清除（renew 永不成功返回数据） | unregistered 复发 ✅ |
| L4 弹窗抑制 | license 窗口不可见 | 弹窗闪烁 ✅ |

### 6.2 校验通过的架构（加载器 vs 校验器双路径）

asar 完整性校验走 **hook 过的 fs**（JS 层 fs.readFile 全被拦截），而 Electron 的 asar require 加载器走 **原生直读**（不经 hook）。因此：

- `app.asar` 内放 **hook 版 launch.dist.js** → 加载器读到 hook → hook 生效
- `resources\app.bak\` 放 **官方原版 4 文件** → 校验器读到原版 → 与 header integrity 一致 → 通过

> [!warning] 重打包铁律
> 重打包**必须原样保留 header 里的 integrity 值**（绝不重算，`fix_rebuild_asar.py` 已固化此逻辑）。jsc 不在校验范围，怎么换都行。

### 6.3 L1 注册表引导

```js
require("child_process").execFileSync(process.env.SystemRoot+"\\System32\\reg.exe",
  ["add","HKCU\\Software\\Typora","/v","SLicense","/t","REG_SZ",
   "/d","QUFBQQ==#0#"+MM_DD_YYYY,"/f"], {stdio:"ignore"});
```
code 内容任意（`QUFBQQ==` = base64 "AAAA"），因为 L2 无条件伪造解密结果。renew 每次剥离 → 下次启动 hook 又写回。

### 6.4 L2 publicDecrypt 伪造

```js
crypto.publicDecrypt = () => Buffer.from(JSON.stringify({
  deviceId:"ZEROJEAN | 28064 | Windows", fingerprint:"t6aaDrYAHd",
  email:"zerojean@mail.local", license:"Cracked_By_ZEROJEAN",
  version:"win|1.13.2", date:<今日 MM/DD/YYYY>, type:"ZEROJEAN"}))
```
probe 模式下只记录不伪造（key 指纹 + 密文 hex），用于换机器时核对字段。应用**不校验伪造字段与真实机器码的一致性**（renew body 直接用伪造字段）→ 可跨机沿用。

### 6.5 L3 renew 拦截

`electron.protocol.handle('https', ...)` 拦截**所有** https（含 electron.net 的请求）；`/\/api\/client\/renew/` 命中 → 返回 `{"success":true,"license":"QUFBQQ==#0#<today>"}`；其余请求 `net.fetch(req,{bypassCustomProtocolHandlers:true})` 原样转发。

### 6.6 L4 弹窗抑制

包装 BrowserWindow：`loadURL` 记录 URL → 含 `license.html` 的窗口 `show/showInactive→skip`、`close→hide`。环境变量 `TY_FORCE_SHOW_LIC=1` 时放行（调试用）。

## 10. 踩坑清单

1. **python3/python 是 WindowsApps 桩** → 必须 `D:/ProgramData/Miniconda3/python.exe` 全路径。
2. **git-bash 复杂嵌套引号必炸**（node -e 内联 3 连败）→ 一律写文件执行。
3. **PowerShell `$` 变量被 git-bash 吞** → 整条命令单引号包裹（§8.2 已如此）。
4. **7-Zip 装不上（UAC）** → 用 innoextract。
5. **inspector.open 必须 wait=false**，wait=true 冻结应用。
6. **CDP 只暴露 node 目标**；渲染器必须主进程 `webContents.debugger.attach('1.3')`；scriptId 是字符串。
7. **renew URL 是 `dian.typora.com.cn`**，先入为主 store.typora.io 必失败。
8. **标准重启流程**：taskkill → rebuild → rm fshook.log → start → sleep 14 → 分析，别省。
9. **rebuild 前必须杀 Typora**（asar 占用会静默失败）。
10. **header integrity 绝不重算**（fix_rebuild_asar.py 已固化，勿"优化"）；app.bak 必须放原版。
11. **jsc 不在校验范围** —— 换 jsc 安全且立即生效（0 读取实证）。
12. **app.bak\atom.compiled.dist.jsc 是无用遗留**，勿放勿依赖。
13. **CodeMirror textContent 是视口虚拟化**，不能当全文（验证脚本注意）。
14. **`[rej] Script failed to execute` 是良性噪音**，别当故障。

## 11. 经验教训

1. **双模式 hook（probe/activate）**：先观察后干预 —— probe 只打点不伪造，把解密输入输出/字段读取/网络流量全部记录下来，机制清楚了再开 activate。
2. **日志驱动逆向**：fs / ipc / JSON.parse / 网络全链路打点，靠日志还原启动序列（unfill→renew→refill 就是这样拼出来的）。
3. **对照实验定根因**：官方 vs 破解 jsc 行为对比，一次实验就排除"激活状态"假说。
4. **先入为主害人**：renew 域名先猜 store.typora.io，实际是中文镜像 dian.typora.com.cn —— 字符串池 / 日志确认后再下结论。
5. **跨重启验证**：注册表/磁盘状态类问题只会在重启后暴露（renew 剥离 code 每次启动发生）。
6. **双路径架构洞见**：加载器（原生直读）与校验器（JS fs）走不同路径 → hook fs 让校验器看原版、asar 内放 hook 版，两边各取所需。
7. **jsc 替换是安全切入点**：完整性校验不覆盖 jsc（0 读取证据），这就是整个修复能成立的支点。
8. **失败的假设要快速证伪**：app.bak 交换方案（换整个目录）无效 —— Electron asar require 直读 asar 内部，必须重打包 asar 本体。
